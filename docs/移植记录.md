## 三、方案（为什么这么选）

**源码**：`oppo-source/android_kernel_oppo_mt6833` 的 `oppo/mt6833_t_13.1.1_a2x_5g`
- A2m 自己只有 `u_14.0.0` 分支，与设备 13.1.1 固件 ABI 不兼容（`module_layout`/`mutex`/`kmem_cache` 全不匹配，1084 个符号里 388 个 CRC 不一致）
- A2x 与 A2 的 13.1.1 分支仅差一个屏幕驱动（`CONFIG_DRM_PANEL_OPLUS23053_TRULY_TD4160_DPHY_VDO`），而设备 `lcm=oplus23053_ili9883c_boe`，故选 A2x
- vendor 私有树 = `android_kernel_modules_oppo_mt6833` 同名分支的 `vendor/`

**构建**：clang-r383902（11.0.1，与设备 `CLANG_VERSION=110001` 一致），保留 `LTO_CLANG + CFI_CLANG + MODVERSIONS`；`localversion=+` 保证 `UTS_RELEASE` 与厂商模块 vermagic 完全一致；关闭 `MODULE_SIG_FORCE`（不影响 `struct module` 布局）。

**Root**：SukiSU Ultra `builtin` 分支（KernelSU 官方 v1.0 起已放弃非 GKI）。手动 hook 7 处：`fs/exec.c`、`fs/open.c`、`fs/read_write.c`、`fs/stat.c`、`kernel/reboot.c`、`fs/devpts/inode.c`、`fs/namespace.c`（回填 `path_umount`）。为 4.19 编译另修 5 类兼容问题（static_call、fallthrough、selinux_hide 版本守卫、KPM/SUSFS 引用守卫、`user_arg_ptr` 传参）。

## 四、WiFi/蓝牙怎么恢复的

原厂 `.ko` 与本内核 CRC 不匹配（`wmt_drv` 10 处、`wlan_drv_gen4m` 53 处，涉及 `struct sk_buff`/`struct net`）。做法是**用同一份 13.1.1 vendor 源码重编配套模块**：

| 模块 | 说明 |
|---|---|
| `wmt_drv.ko` | 连接子系统核心 |
| `wmt_chrdev_wifi.ko` | 提供 wlan 依赖的 `wifi_reset_*` 等符号 |
| `wlan_drv_gen4m.ko` | **SOC2_1X1 + HIF=axi**（关键：用错 chip/HIF 会固件加载失败） |
| `bt_drv_connac1x.ko` / `gps_drv.ko` / `fmradio_drv_*.ko` / `connfem.ko` | 其余连接模块 |

编译要点：`MTK_PLATFORM=mt6853`、`TOP=<modules 仓库根>`、`MTK_ANDROID_WMT/EMI=y`、`MTK_WLAN_SERVICE=yes`，并给 `plat/mt6833/plat_priv.c` 补回 `#include "wmt_exp.h"`。

**加载方式**：不塞 ramdisk（实测会被 first-stage init 中止启动），改用 **KSU 模块开机脚本**：
`/data/adb/modules/a2m_connsys/post-fs-data.sh` 在 `post-fs-data` 阶段（早于 zygote）按序 `insmod`，7 个模块 rc=0，WiFi 自动连接。

## 六、SUSFS 与 KPM（本版已打通）

### 关键结论：4.19 没有 v2 补丁，所以走"混合实现"

SukiSU v4.2.1 的命令层用的是 **SUSFS v2.3.0 的 ABI**（`void susfs_xxx(void __user **)` + 带 `err` 字段的结构体），
而上游 susfs4ksu 给 4.19 的补丁只到 **v1.5.5**，两者结构体布局与函数签名都不同（例如 `open_redirect`
在 v1.5.5 里前面多一个 `target_ino`，直接混用会读错偏移）。

本版的实现方式：

- **内核核心**：采用 v1.5.5 的 4.19 原生实现（含 sus_path 的 inode 标记、sus_mount 的 mnt_id 伪造、sus_kstat 的 stat 伪造），
  这些代码是上游针对 4.19 写好的，稳定性最好。
- **ABI 层**（`fs/susfs_abi.c`）：把 v2.3.0 的 16 条命令翻译成 v1.5.5 核心调用，结构体统一为 v2 布局，
  因此管理器（SukiSU 4.2.1）看到的就是它期望的 v2.3.0。
- **补齐 v2 独有能力**：`sus_map`（从 `/proc/pid/maps`、`smaps` 中剔除指定映射）、
  `avc_log_spoofing`（把 ksu 域的 avc 拒绝日志伪装成 `priv_app`）、
  `enabled_features` / `variant` / `version`、`priority_uid_filter`、`sus_path_loop`。
- **隐藏判定的修正**：v1.5.5 的钩子依赖 `current->susfs_task_state`，而这版 KernelSU 不再维护它，
  直接照搬会导致"永远不隐藏"。已改为动态判定 `susfs_is_current_app_uid()`（`uid % 100000 >= 10000`），
  与 v2 的语义一致。

编译期可见 SukiSU 侧识别结果：

```
-- SukiSU-Ultra: using SUSFS_INLINE_HOOK
-- SUSFS_VERSION: v2.3.0
```

符号表确认（72 个 `susfs_` 符号，含全部命令入口）。

### KPM：注入 KernelPatch 后才真正可用

KPM 不是普通 ioctl，而是通过 `__arm64_sys_truncate` 的超级调用与 **KernelPatch** 通信。
官方 KernelPatch 二进制不带 SukiSU 的 magic（`0x53554b504d000002`），必须用
[SukiSU_KernelPatch_patch](https://github.com/SukiSU-Ultra/SukiSU_KernelPatch_patch) 里那份定制 `kpimg`。

本版流程：

```
gunzip Image.gz → kptools -p -i Image -k kpimg -o Image.patched → gzip → 重新打包 boot
```

`kptools -l` 回读显示 `patched=true`，且能定位到 `paging_init`、`avc_denied` 等挂载点。

## 八、2026-10-27 二次尝试：SUSFS 已进内核，管理器仍异常

### 已解决：开机即崩的根因

`pstore/console-ramoops-0` 抓到崩溃点：

```
pc : ksu_handle_stat+0x20/0xb4
Call trace: ksu_handle_stat ← vfs_statx ← clean_path ← unpack_to_rootfs
```

根因在 `drivers/kernelsu/feature/sucompat.c`：第 42 行 `#ifdef CONFIG_KSU_SUSFS`
分支是给 5.x 写的（参数 `struct filename **`，内部按 `(*filename)->name` 取值），
4.19 一旦打开 SUSFS 就会编进这套实现，而 `vfs_statx` 传的是 `const char __user *`，
于是把 `"dev"` 字符串的内容当指针解引用 → 上电 1 秒内 data abort。

修复：

- 该分支加上内核版本限制：`#if defined(CONFIG_KSU_SUSFS) && LINUX_VERSION_CODE >= KERNEL_VERSION(5,0,0)`
- `sucompat.h` 同步分流
- 4.19 分支补齐 sulog 参数类型、adb_root 接口改名
- `ksu_handle_execveat` 里 ksud 处理完不再 `return`，继续走 sucompat

### 最后一处关键修复：seccomp 与驱动 fd

管理器此前一直显示「内核上未检测到 SukiSU 驱动程序」，日志里是：

```
ksud::ksucalls: KernelSU driver install syscall was blocked by seccomp
could not retrieve kernelsu driver fd
```

根因有两层，都在 4.19 的 SUSFS 分支上：

1. `drivers/kernelsu/hook/lsm_hook.c` 里 `task_fix_setuid` 钩子被 `#ifndef CONFIG_KSU_SUSFS`
   排除，改用 `ksu_handle_setresuid()`；但 4.19 的 `kernel/sys.c` **从未调用**它，
   所以 zygote 孵化的应用既不会关 seccomp，也拿不到驱动 fd。
2. 即使补上调用点，`susfs_zygote_sid` 在 4.19 上恒为 0（`susfs_set_batch_sid()` 只在
   5.10+ 的策略加载路径里被调用），sid 比对永远失败。

修复：

- `kernel/sys.c` 的 `__sys_setresuid()` 里调用 `ksu_handle_setresuid()`
- `ksu_handle_setresuid()` 首次进入时补设 sid（此时 SELinux 策略已加载），
  仍失败则退化为按 uid 判定，保证管理器能关 seccomp 并安装 fd

修复后日志：`sid '76' is set for secctx_name 'u:r:zygote:s0'`，管理器随即恢复。
